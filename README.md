# stompbox

The safest way to ship a multi-user Effect app on Postgres: the database
decides who may read and write each row, and tests prove it.

The patterns come from `~/build/effect-web-template` and seven apps (dfg.codes,
dfg.rocks, postgres.garden, knowledgebase, setlist, twitter-bookmarks, budget).
The apps are evidence and possible future consumers. None of them is migrated
until the design is settled.

## What it is

Versioned packages own the security-critical code and SQL, so a fix reaches
every app through an upgrade. An app template holds everything else as plain
Effect code that the app owns. The project specializes only where Postgres
buys a guarantee that Effect cannot give, and stays generic everywhere else
(`docs/adr/0005-packages-and-a-template.md`).

## Plan

Each step ends with a check that does not depend on our own opinion.

1. **Security checker.** The security rules as checks that run against a live
   Postgres database, for any app that uses row-level security. Check: run it
   against each surveyed app at the commits that hold the known bugs; it must
   flag every bug that is a property of the SQL.
2. **Visitor transaction library.** The role contract check at startup
   (ADR 0002), the session bridge (ADR 0004), and database error mapping.
   Check: the security checker passes on the reference app. Step 2b adds
   visitor handles typed to what the visitor may reach (generated by
   pg-sourcerer, after its role inheritance fix). Check: a query outside the
   visitor's reach fails to compile.
3. **Auth SQL with upgrades.** First the schema delivery design and its ADRs
   (prior art: Django per-app migrations, Supabase's auth schema,
   graphile-migrate). Then the auth package, with the SQL of each feature
   installed and upgraded in dependency order. The choice between the starter
   SQL and Yielded Auth (`docs/research/yielded.md`) decides how much SQL it
   holds. Check: after an upgrade across two versions, `pg_dump --schema-only`
   equals a fresh install.
4. **Template and reference app.** Config, `HttpApi`, telemetry, the worker and
   tests, wired with plain Effect. The reference app is knowledgebase
   (`examples/knowledgebase/`): its server was written first as it should
   read, and the packages change until it compiles. Checks: the reference app
   passes its tests on Bun and on Node with no patches to package internals; someone other than the author builds a multi-user app
   from the docs alone.

A council review comes before the code of each package.

## Release

`bun run release` tags the version in `package.json` at HEAD as `v<version>`.
It runs typecheck, lint and build, then commits the built `dist/` on a
temporary worktree and tags that commit. The current branch and the main
checkout do not move. The tag stays local: the command prints
`git push origin v<version>` for you to run. The test suite is not part of the
gate, so run it before you release.

The command refuses when the working tree has changes or the tag already
exists. Apps install the tag with `bun install --ignore-scripts`
(`docs/adr/0009-one-package-tagged-on-github.md`).

## Rules

- Code goes into a package only where at least three apps already do the
  same thing (`docs/matrix/`). Security rules are the exception: they
  come from bugs, so a package enforces them even when no app does yet.
  Features that only the template has still need three apps.
- Auth, migrations and the worker require Postgres (ADR 0001).
- A second adapter for a service ships only when an app uses it or Effect
  provides it (ADR 0003).

Terms are in `GLOSSARY.md`. Decisions are in `docs/adr/`.
